old address.

## The source

`www/` is a separate Vite project (own lockfile, plain JavaScript, one stylesheet) sharing no
dependency with the app.

```bash
npm run site:dev        # site only, :5280, hot reload
npm run build:web       # editor + site, assembled into dist-web/
npm run site:preview    # build:web, then serve each host as deployed (:4174 site, :4175 editor, :4176 old address)
npm run e2e:web         # checks against the assembled artifact
```

Run `site:preview` before shipping: `scripts/serve-web.mjs` mimics the hosts' trailing-slash
redirects and 404 pages.

The landing page uses the editor's neutral charcoal and white palettes, with the existing
`www/scripts/og-illustration.png` as its main artwork. SVG stroke masks reveal the original charcoal pixels along the board, people, connectors and Nodi
contours. A luminance-to-alpha SVG filter removes the bitmap’s dark paper and gives its strokes
the same neutral ink as the diagram; the meeting recedes as the camera moves down. **Draw again** replays the complete drawing; **Finish drawing** shows the finished plate
immediately. Reduced-motion preferences show the static artwork. The sequence starts when the
illustration enters the viewport, and leaves the original image in place when complete.
The drawing has unlabelled interactive regions: hover or focus to trace a request, reveal a
service cutaway, or explore Nodi, collaboration and an open question. Touch activation offers
the same visual responses. No interaction runs an agent or starts a session.

Monochrome paper grain and broad graphite washes span the drawing and reading columns without intercepting input.
The washes drift slowly using a transform animation; reduced-motion preferences keep them still.
The visible free-and-open-source message appears once, in the footer.

The page follows one question, “what happens next?”, on one charcoal surface. The camera moves
from the meeting sketch into real product footage and captures. The six priorities are request-flow
presentations, Nodi's review workflow, C4 depth, repository source evidence, live collaboration,
and open points. Drawing conveniences and import/export support the closing ownership message. Desktop is the
primary destination: the header, opening and closing calls to action open the installer chooser.
The installer chooser names macOS and Windows. The page connects Nodi and repository workflows to desktop and keeps
the browser editor as a secondary try-it link.

`recordedStory.js` plays muted recordings at 0.8× speed once their explanation is in reading
position. Scrolling selects chapters without scrubbing frames. Videos pause during handoffs or
when the page is hidden, hold their final frame, and offer pause and replay controls. It uses the existing
presentation and look-inside clips plus a Nodi-only cut of the release recording (the collaboration
segment and closing slate are excluded by `www/scripts/clips.mjs`). Source evidence uses an actual editor screenshot, labeled as a capture. Collaboration uses `clips/collaboration-paired.mp4`, captured from a disposable real editor session over
local WebRTC: Cris asks to join, the host admits them, Cris edits and moves Orders API, the host

retains the updated canvas. Both views are captured together and stay side by side throughout, labeled Alex / host and Cris / teammate.
The active service is framed closely enough to see the shared label and position changes. Browser-rendered
frames are encoded as a 1600×900, 30 fps MP4 with reading holds and the shared 0.8× playback rate.
Dialog backdrops are excluded spatially, preserving the contrast of the actual dialog text and sketches.
This standalone capture is not regenerated by `clips.mjs`. Open points uses `clips/open-points.mp4`, captured from the real editor's Order processing
example: open the Orders API context menu, add an awaiting-input point, type the retry question,
close it, then open the review list. The capture was assembled from browser-rendered frames with
readable holds, encoded as a silent 1280×720 H.264 MP4 at 30 fps; it plays at the same 0.8× rate.
Unlike the reel excerpts, this standalone capture is not regenerated by `clips.mjs`.
Light and dark assets use separate luminance-to-alpha filters to become neutral ink, with a pencil
outline and edge mask tying them into the canvas. Captures stay still; reduced motion
shows static midpoint video frames and fully revealed captures. Media is loaded only when the
story approaches the viewport. Failed loads expose a retry control. These recordings do not connect a live session or change a visitor’s document.

The outgoing meeting connector stays hidden at the opening and starts only after scrolling.
The demo itself stays hidden until its first chapter reaches the reading position, then draws into
view with a scroll-controlled reveal. The connector finishes before that reveal; playback starts
after the reveal and holds at the end of each chapter. Returning to the opening hides it completely. The C4 chapter omits the setup dialog and its dimmed backdrop. It
includes the return to the overview. A persistent sketch depth navigator follows the decoded
recording frames: its component layer unfolds on entry and collapses on return. Its overview
button folds the current component drawing into the service while the overview reappears, with
the depth stack collapsing in sync. Reduced motion returns immediately. Changing chapters cancels the return. Chapters use 1.35 viewport heights rather than long empty scroll runways. Chapter copy stays pinned beside the canvas, and playback
starts only after the explanation reaches its reading position. Chapter handoffs share one
scroll-driven opacity and movement envelope across the copy, canvas and caption. Outgoing ink
clears before incoming ink appears; media is revealed only after its matching frame has decoded.
**See it in the real editor** opens the original demo video in a native dialog, only on request.
Marketing styles are scoped with `.studio` so documentation retains its reading layout.
There are no webfonts.

## The build

- `www/vite.config.js` replaces `__VERSION__` with the root `package.json` version for download links.
- It generates the CSP, hashing the one inline script, with `connect-src 'none'`.
- `scripts/assemble-web.mjs` builds `dist-web/` from `site/` (`www/dist/`), `app/` (`dist/`),
  `legacy/` (`www/legacy/` plus `dist/` under `editor/`) and `cloudflare/` (Wrangler configs), then
  checks each part. `dist/` is left unchanged.

## The documentation

`docs/` is the only copy of the docs. The site build renders it under `/docs/`.

- **Published:** `docs/index.md`, every guide, and `PUBLISHED_REFERENCE` in `www/scripts/docs.mjs`
  (privacy and agent integration). Links to anything else go to GitHub.
- **Sidebar:** the rows of the tables in `docs/index.md`, in order. A new guide appears once listed
  there.
- **Link checks:** a link to an unpublished page, anchor or image fails `npm run site:build`. Anchors
  use GitHub's slug rule, as in `tests/docs.test.ts`.
- **Release timing:** pages ship from the release tag, so doc changes go live with the next release.

With `npm run site:dev`, refresh `http://localhost:5280/docs/` to see an edit.

## Deploying

`pages.yml` is the only deploy workflow.

1. Cloudflare first, with Wrangler: relay, `app/`, `site/`, then the `www.` redirect. The relay and
   `app/` only for a release or a withdrawal; otherwise just `site/` and the redirect.
2. Then `legacy/` to GitHub Pages, only if Cloudflare succeeded.

Triggers (all share the `pages` concurrency group):

- **Release:** `release.yml` passes the verified artifact after CI and desktop acceptance.
- **Site change:** `pages-site.yml` calls it on a push to `main` touching `www/`,
  `scripts/assemble-web.mjs` or either Pages workflow. It waits (skips) while `package.json` names a
  version that is not the latest published release; that release's deploy publishes it instead.
- **On demand:** run it from `main` (site only, unless `release-tag` is set).

Off a release tag, `pages.yml` builds the newest stable `vX.Y.Z` with this commit's `www/` and
`scripts/assemble-web.mjs` laid over it, and tests it in Chromium, Firefox and WebKit. The relay and
the editor's hosting (`relay*.js`, `relay.jsonc`, `app.jsonc`, `app.headers`) come from the release
wherever it has them, and are not deployed. So the editor, docs, relay and the editor's headers change
only on a release; a push touching `www/cloudflare/` waits for the next one.

**Withdrawal:** run `pages.yml` from `main` with `release-tag` set to the last good tag. Follow
[the recovery procedure](reliability.md#withdrawal-and-recovery-procedure) first.

### Cloudflare

Each config in `www/cloudflare/` names its custom domain; `wrangler deploy` creates the DNS record and
certificate. Repository secrets:

- `CLOUDFLARE_ACCOUNT_ID`: the account holding the `draftcanvas.dev` zone.
- `CLOUDFLARE_API_TOKEN`: limited to that account and zone, with **Account › Workers Scripts › Edit**,
  **Zone › Workers Routes › Edit**, **Zone › DNS › Edit** and **Zone › Zone › Read**.

The relay's Durable Object needs nothing more; its migration in `relay.jsonc` applies on deploy.

Wrangler is pinned in `www/cloudflare/package.json` and its lockfile (`npm ci`, then
`npx --no-install wrangler`). To upgrade, change the version and run `npm install --package-lock-only`
there.

`app.headers` becomes the editor's `_headers`. It prevents framing with an HTTP CSP
`frame-ancestors 'none'` directive and `X-Frame-Options: DENY` for older browsers. This header policy
adds to the editor's build-generated CSP meta tag; `frame-ancestors` cannot be enforced through a
meta tag. Never set `Cross-Origin-Opener-Policy` there: it breaks the old-address handoff, which uses
`window.opener`.

### Edge TLS policy

The editor is a **Worker custom domain** (`www/cloudflare/app.jsonc`), not a Cloudflare Pages
hostname. Cloudflare terminates visitor TLS before serving the Worker; HTTP headers and Wrangler's
`compatibility_date` do not select TLS versions.

The intended edge policy is **minimum TLS 1.2, with TLS 1.3 enabled**. TLS 1.0 and 1.1 must be refused;
TLS 1.2 remains available for compatibility and supported clients negotiate TLS 1.3. These are
Cloudflare zone settings, managed separately from the repository's deploy. See Cloudflare's
[minimum TLS version](https://developers.cloudflare.com/ssl/edge-certificates/additional-options/minimum-tls/)
and [TLS 1.3](https://developers.cloudflare.com/ssl/edge-certificates/additional-options/tls-13/) references.

**Review the scope before applying:** the free zone setting affects every proxied hostname in
`draftcanvas.dev`, including the apex, `app`, `www`, `relay` and any others. Clients that only support
TLS 1.0 or 1.1 lose access. Per-hostname minimum TLS requires Advanced Certificate Manager; if other
hostnames need a different policy, review that option instead of changing the whole zone. Existing
hostname overrides can take precedence over the zone setting.

After approval, an operator with access to the `draftcanvas.dev` zone should:

1. Review the zone's hostnames, existing TLS overrides and client compatibility. Record the existing
   **Minimum TLS Version** and **TLS 1.3** values before changing them.
2. Open **SSL/TLS → Edge Certificates** in that zone. Set **Minimum TLS Version** to **TLS 1.2**.
   Keep **TLS 1.3** enabled, or switch it **On** if disabled. Leave other TLS and cipher settings alone.
3. Check the zone settings with `node scripts/check-cloudflare-tls.mjs`. Supply `CLOUDFLARE_ZONE_ID`
   and a separate `CLOUDFLARE_TLS_API_TOKEN` through the environment. Restrict this token to
   `draftcanvas.dev`, with **Zone › Zone › Read** and **Zone › Zone Settings › Read** permissions.
   The checker makes only GET requests, rejects a different zone, and exits nonzero for a policy
   mismatch or failed read. Do not broaden the deployment token's permissions for this check.
4. Request a fresh [SSL Labs assessment](https://www.ssllabs.com/ssltest/analyze.html?d=app.draftcanvas.dev).
   On every reported IPv4/IPv6 endpoint, confirm TLS 1.0/1.1 are rejected and TLS 1.2/1.3 are supported.
   Verify affected site and relay clients still connect. A successful settings check alone does not
   prove the effective policy at each hostname or edge.
5. After deploying header changes, request a fresh
   [HTTP Observatory scan](https://developer.mozilla.org/en-US/observatory/analyze?host=app.draftcanvas.dev)
   and confirm the framing check passes. TLS settings and HTTP header deployment are separate steps.

Neither the read-only checker nor the normal deploy applies the zone TLS policy. If a compatibility
issue requires rollback, an operator can restore the recorded values in **Edge Certificates**;
restoring a minimum below 1.2 also restores support for the older protocols.

### The collaboration relay

The relay carries a [live session](../guides/collaborating.md)'s knock, offer and answer until the
browsers connect directly.

- **Sees:** encrypted messages, a random 128-bit room id, origins, IP addresses, sizes and timing.
- **Stores:** only the owner claim, a SHA-256 of the secret in the handshake
  (`Sec-WebSocket-Protocol: draft-canvas.relay.v1, host.<secret>`); another host is closed with 4003.
  Each owner connection or departure renews the claim for 12 hours.
  No logging; observability is off in `relay.jsonc`.
- **Limits:** one owner and 32 joining sockets per room, at most 4 of them from one address (per /64
  for IPv6); text frames with at most 16,384 characters of data; 30 messages per 10 seconds per
  socket, and the owner that much for every joining socket, since it answers each of them (past it,
the owner's frames are dropped, never its socket); 60 new
  sockets per minute per address. A room closes after 15 idle minutes, or 12 hours at most. The
  owner's own reconnect replaces a socket the relay still thinks is open.
- **Origins:** only `ALLOWED_ORIGINS`; by default the web editor and the desktop app.

Code:

- `www/cloudflare/relay-room.js`: every rule, no Cloudflare code. Tested by `tests/relay-room.test.ts`.
- `www/cloudflare/relay.js`: the Durable Object adapter.
- `scripts/dev-relay.mjs`: a Node relay for development and e2e (`npm run dev:relay`, port 8791),
  also admitting `http://localhost:*` and `http://127.0.0.1:*`. Tested by `tests/dev-relay.test.ts`.

Builds read `VITE_COLLAB_RELAY` (default `wss://relay.draftcanvas.dev`; `ws://localhost:8791` under
`npm run dev`; empty for none) and add it to the CSP's `connect-src`.

- **Your own relay:** deploy `relay.js` as your own Worker, or anything with the same contract, and
  set `ALLOWED_ORIGINS` to your editor's origin. Build with `VITE_COLLAB_RELAY=wss://…`; see
  [Self-hosting](../guides/self-hosting.md#live-sessions).
- **Desktop:** its CSP is fixed in `src-tauri/tauri.conf.json`; add another relay there too.

## The move to draftcanvas.dev

IndexedDB is per origin, so diagrams saved at `acltabontabon.com/draft-canvas/editor/` are invisible
to `app.draftcanvas.dev`.

- **Change-of-address page:** `www/legacy/` has no build step. Its `404.html` forwards other old
  paths to the same path on `draftcanvas.dev` (`/editor/…` to the app).
- **Handoff:** the old editor shows **Bring my diagrams**. It opens `app.draftcanvas.dev/#handoff` and
  sends a Library backup with `postMessage`; both sides check the exact origin and window. The new tab
  restores it without overwriting (taken ids arrive as copies). Protocol: `src/storage/handoff.ts`.
  Manual route: **Back up** on the old address, **Restore** on the new.
- **Path-independent storage:** database names and the `draft-canvas.` preference prefix never derive
  from the path; `tests/privacy.test.ts` enforces it. That is why the editor could move to `/editor/`.
- **Old service worker:** `www/legacy/sw.js` replaces the one that served the editor at
  `/draft-canvas/`, deletes only its own caches and unregisters.
