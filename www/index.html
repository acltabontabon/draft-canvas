Chapter 01 of 06

Shapes that already know what they are

A small vocabulary, not a shape browser

A service is not a rectangle with a label on it. It is a service — so when you drag a connector from it to a queue, Draft Canvas writes publishes to on the line, because that is the only thing that connection could sensibly mean. Drag the same connector to a database and it says writes to instead.

That is the whole trick, and it is why the diagram stays readable while you are talking over it. You spend your attention on what the system does, not on picking a line style and typing a caption for the fourth time.

Ten shape types, each with a handful of kinds. Every one of them drops with a single keystroke — S for a service, D for a data store, Q for a queue — and the whole palette is on ⌘K when you would rather read than remember.

It offers the next move. Once.

Predictable conveniences, not predictions

Draw a queue and press ]. A worker appears in ghost beside it, already connected, already labelled consumed by. Tab keeps it. ] again shows the next candidate, [ goes back, and ignoring it costs nothing — the ghost never becomes real on its own.

Where the answer genuinely is not obvious — a table that could be an outbox or a read model — it declines to guess and opens the picker instead, with the reason written above it. Silence is the default; it only speaks up when it is confident.

This is a lookup table and a capability matrix, written by hand and checked by tests. No model, no inference, no network. The same shape offers the same next move today as it did last month, which is the only reason it is safe to press without looking.

Chapter 03 of 06

Or start composed

Four letters to a whole architecture

Sometimes the fastest way to explain a system is to put a familiar shape of one on the canvas and start deleting. Type a pattern's name into ⌘K and it arrives composed — laid out, connected, with its flows already built so you can present it immediately.

None of it is special. There is no template object, no locked group, no starter marker anywhere in the file. It is ordinary shapes and ordinary connectors, and the empty space around them is deliberate: a starter is the first thirty seconds of a diagram, not a reference architecture, and certainly not advice about how to build yours.

04

Chapter 04 of 06

Walk the room through it

Each step brings its own notes and code

A finished diagram is a wall of boxes to everyone who did not draw it. So group the connectors that tell one story into a flow — Submit command, Compensation, Read projection — and present it a step at a time. Everything outside the flow dims rather than disappearing, so the room can still see where they are.

The note you pinned to a connector three weeks ago comes back on the step it belongs to. So does the payload you pasted in. That is the point of pinning it there instead of keeping it in your head or in the slide you did not make.

Somebody says wait, who retries that? Capture it as an action without leaving the presentation, and copy the whole list out as Markdown when you are done. The decisions and open questions are already there — they are the notes on the canvas, tagged as what they are.

05

Chapter 05 of 06

Look inside

C4-aware, in one canvas

The overview should stay small enough to hold in your head. So the detail goes inside: select a service, press ⌘↓, and you are on a fresh canvas that belongs to that service. ⌘↑ comes back out. A depth map along the top shows what contains what, and where you are in it.

A canvas can say which level it is — system context, containers, components, or nothing in particular — and Draft Canvas will quietly stop offering things that make no sense at that level.

It narrows what it offers. It never refuses what you draw. There is no validator, no compliance score, no red underline telling you your architecture is wrong. When a diagram looks like a system overview, it asks once — and if you say nothing, nothing is stored. It is a drawing tool that knows about C4, not a modelling tool that grades you.

06

Chapter 06 of 06

Throwaway, but exportable without disappointment

Seven ways out, and a file you can diff

Most of what you draw in a meeting deserves to be thrown away. The rest needs to leave cleanly — into a pull request, a design doc, a chat thread, or a ticket — without becoming somebody's afternoon.

A .draftcanvas file is plain JSON with a fixed field order, so saving an unchanged diagram twice produces identical bytes. It diffs. It reviews. It belongs in the repository next to the thing it describes.

A flow can also leave as a sequence diagram — Mermaid or PlantUML source text, not a picture of one. That is a different job from exporting the diagram itself: one gives you the architecture, the other gives you the walkthrough as code your docs can render.

  • .draftcanvasEditable JSON. Byte-stable, diffable, what the desktop app and VS Code save.
  • .dcencThe same file behind a passphrase you choose. PBKDF2, 600,000 iterations, fresh salt.
  • .pngRendered at 2× by default, in the theme you are working in.
  • .svgVector, with the text as text.
  • .gifA flow playing itself, for a chat thread that will not open a link.
  • .mmdMermaid sequence-diagram source, built from a flow.
  • .pumlThe same, as PlantUML.

Revision 1.12 · in the desktop beta

Your agent sketches in pencil. You ink it.

Draft Canvas speaks MCP, so the agent in your editor can draw

Ask Claude Code or Cursor to draw how orders move through the repository you have open. It reads the code, then hands Draft Canvas a description — the parts, how they connect, the flows. Never a coordinate. Draft Canvas lays it out, routes it and draws it as an ordinary diagram: yours to move, present and export.

Follow-ups change the same diagram — add a dead-letter queue, rename that service, explain the retry in a note. Each one lands as a single undo step, and what you arranged by hand stays where you put it. While the agent works, its change is drawn faintly over yours: pencil, until it lands.

Or tell it not to touch anything. Review this pull request against the diagram comes back as a proposal — every addition, change and removal, the actual before and after, and the agent’s reasoning. Nothing is inked until you press Accept.

Off until you turn it on, and only in the folders you tick. Draft Canvas sends your diagrams nowhere; your agent talks to its own AI provider, as it already does with your code. Nothing an agent is still preparing is saved, undoable, or in the file until it lands.

Three trades, made on purpose

What Draft Canvas optimises for

  • speed over completeness
  • opinion over configurability
  • throwaway but exportable without disappointment

Every one of those costs you something. They are written down in the repository, in these words, because a tool that will not say what it is bad at is not telling you what it is good at either.

What “local-first” means here, exactly

In the browser, diagrams live in IndexedDB. The body of each one — every label, note and snippet — is encrypted with AES-256-GCM before it is written, under a key generated in this browser that no code path can read back out. Its title and shape counts are not encrypted, so the Library can list it.

On the desktop and in VS Code, the file on disk is the storage: plain JSON, yours to move, diff and back up. It is not encrypted, because it is a file in your repository, and it should behave like one.

Nothing syncs between them. Three separate places, on purpose. Moving a diagram between them means exporting it and opening it, which is a file operation you can see happen.

The app makes no network requests of its own — a test in the suite fails on any call in its source, and the shipped page's own security policy forbids reaching another origin. The one exception is the service worker fetching a newer copy of the app itself. What is stored, in detail.
